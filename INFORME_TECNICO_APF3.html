1. Información del Proyecto y Grupo de Trabajo

EcoTechTrack es una solución de software web de alta escala diseñada para resolver la problemática de trazabilidad de los Residuos de Aparatos Eléctricos y Electrónicos (RAEE) en instituciones corporativas y públicas del Perú, cumpliendo con la directiva y lineamientos del Ministerio del Ambiente (MINAM).

1.1 Objetivos de la Integración (APF3)

  1. Desarrollar una interfaz de usuario moderna y responsiva con Angular 18 utilizando componentes autónomos (Standalone Components) y estilos en SASS.
  2. Implementar formularios reactivos robustos para el alta y edición de residuos, incorporando validaciones síncronas de formato, campos obligatorios y rangos numéricos.
  3. Consumir la API RESTful de Spring Boot 3 mediante el cliente HttpClient, soportando todos los verbos HTTP (GET, POST, PUT, PATCH, DELETE).
  4. Garantizar la seguridad integral basada en JSON Web Tokens (JWT) mediante un interceptor HTTP en el cliente que adjunte automáticamente la cabecera Authorization: Bearer <token>.
  5. Proteger las vistas y rutas sensibles mediante AuthGuards y control de acceso basado en roles (RBAC) para perfiles ROLE_ADMIN, ROLE_OPERADOR y ROLE_USER.

2.2 Interceptor de Seguridad HTTP (JWT Interceptor)

En src/app/interceptors/jwt.interceptor.ts, se configuró una función interceptora (HttpInterceptorFn) que añade automáticamente el token a las solicitudes y gestiona la caducidad de la sesión: 

export const jwtInterceptor: HttpInterceptorFn = (req, next) => {
  const authService = inject(AuthService);
  const router = inject(Router);
  const token = authService.getToken();

  let authReq = req;
  if (token) {
    authReq = req.clone({
      setHeaders: { Authorization: `Bearer ${token}` }
    });
  }

  return next(authReq).pipe(
    catchError((error: HttpErrorResponse) => {
      if (error.status === 401) {
        authService.logout();
        router.navigate(['/login'], { queryParams: { sesionExpirada: 'true' } });
      }
      return throwError(() => error);
    })
  );
};

3.2 Validaciones en Autenticación y Registro (LoginComponent & RegisterComponent)

  • Usuario (Username): Obligatorio, longitud entre 3 y 50 caracteres. No admite caracteres especiales que puedan comprometer la URL.
  • Contraseña: Obligatoria, longitud mínima de 6 caracteres. Es validada en cliente antes de ser enviada al endpoint seguro donde se procesa con el algoritmo BCrypt.
  • Correo Electrónico: Validador estricto de formato RFC mediante Validators.email.
  • RUC de Empresas Gestoras: Validación de formato tributario peruano mediante expresión regular de 11 dígitos numéricos: Validators.pattern(/^[0-9]{11}$/).
Manejo de Retroalimentación Visual (UX): Los controles aplican dinámicamente la clase CSS .is-invalid únicamente cuando el campo es inválido y ha sido manipulado por el usuario (control.invalid && control.touched), evitando mostrar alertas rojas antes de que el usuario interactúe con el formulario.

4. Problemas Enfrentados en la Integración y Solución Técnica

Problema 1: Bloqueo de Peticiones por CORS (Cross-Origin Resource Sharing)

  • Síntoma: El navegador bloqueaba todas las solicitudes HTTP desde http://localhost:4200 hacia http://localhost:8080 indicando No 'Access-Control-Allow-Origin' header is present.
  • Causa: Spring Security 6 restringe el intercambio de recursos entre orígenes diferentes por defecto y rechaza las solicitudes de pre-verificación OPTIONS (pre-flight requests).
  • Solución: Se implementó un bean CorsConfigurationSource en SecurityConfig.java configurando orígenes permitidos (allowedOriginPatterns("http://localhost:[*]")), métodos habilitados (GET, POST, PUT, PATCH, DELETE, OPTIONS), cabeceras admitidas y allowCredentials(true).

Problema 2: Incompatibilidad de Sintaxis de Plantilla en Angular 18 con Anotaciones Java

  • Síntoma: Error de compilación NG5002: Incomplete block "PreAuthorize" en el build del frontend.
  • Causa: Angular 18 introdujo la sintaxis de bloques de control de flujo nativos (@if, @for). Al incluir el texto explicativo @PreAuthorize en el template HTML, el compilador lo interpretaba como una directiva de control mal formada.
  • Solución: Se escapó el carácter @ utilizando la entidad HTML estándar &#64;PreAuthorize.

Problema 3: Manejo de Sesiones Stateless y Pérdida de Autenticación

  • Síntoma: En peticiones sucesivas, Spring Security intentaba verificar sesiones basadas en cookies JSESSIONID que no existían, provocando respuestas HTTP 401 Unauthorized inesperadas.
  • Causa: Configuración híbrida por defecto entre sesiones de servidor y tokens sin estado.
  • Solución: Se forzó la política de sesiones como estrictamente SessionCreationPolicy.STATELESS en Spring Boot, asegurando que cada petición se valide de forma autónoma a partir del token Bearer JWT contenido en la cabecera.
